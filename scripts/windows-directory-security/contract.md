# Windows directory-handle experiment

This scripts-only unit is not connected to product code. It prepares one prerequisite for private Windows storage; portable result/property, workflow, TypeScript and lint checks pass. Native compilation and acceptance remain pending until the Windows job executes these exact inputs.

The first native CI attempt reached the builder but failed before compiler dispatch because its fixed Visual Studio 2022 directory was absent. The actual `windows-2025-vs2026` image `20260907.229.1` lists Visual Studio Enterprise 2026 at `C:\Program Files\Microsoft Visual Studio\18\Enterprise` in its [exact image inventory](https://github.com/actions/runner-images/blob/win25-vs2026/20260907.229/images/windows/Windows2025-VS2026-Readme.md). The builder now uses that fixed root; it still reads and validates the installed toolset version and compares compiler/header hashes around compilation. The 33 portable tests passed in that run, but compilation and all 18 native cases remain unqualified until a fresh successful run. This root binding does not make the mutable runner image an immutable toolchain pin.

The next attempt reached the compiler and joined its output streams before reporting a nonzero exit. Failed builds now project at most 32 diagnostics containing a known public source basename, bounded line and optional column, severity, and MSVC code. Compiler or linker diagnostics without a source location contain only the fixed tool name, severity, and code. The existing total output bound remains 128 KiB; raw diagnostics stay in memory and no compiler retry occurs. This summary diagnoses a failed attempt and grants no build or native acceptance.

The C core accepts ownership of an already-open directory handle only after observation succeeds. It reads the current process `TokenUser` itself and refuses any thread token, including impersonation it cannot inspect. It requires a non-inheritable disk handle, local NTFS with persistent ACLs and a volume-GUID name, a directory without a reparse attribute/tag or pending deletion, and stable volume serial plus 128-bit file ID around the security read. The name is used only to reject remote volumes; it grants no pathname or ancestor authority.

The DACL must be present, non-null and protected, with one explicit `ACCESS_ALLOWED_ACE` for the exact current user and exactly `FILE_ALL_ACCESS`. This deliberately narrow self-only policy permits that owner to manage its directory. Inherited entries, propagation flags, other principals, generic access masks, deny/object/callback ACEs and unknown descriptor-control bits are refused. An optional bounded group SID is structurally checked but grants no authority. The core reads at most 16 KiB of self-relative descriptor data into a fixed buffer and checks offsets, lengths and disjoint regions before traversing owner/ACL/SID bytes. It neither allocates according to an untrusted descriptor length nor writes security.

`wd_adopt` transfers the original handle only on success. Its private binding retains the original user and file identity. `wd_revalidate` observes the same retained handle and poisons the binding on refusal; a subsequent successful ACL repair by the fixture cannot reopen that binding. `wd_same_directory` revalidates two retained bindings and compares their original file identities. `wd_close` attempts the exact retained close once; a failed close retains a poisoned binding and reports uncertainty. No SID, descriptor, HANDLE or file ID crosses the native JSON boundary.

The fixture alone creates fresh objects beneath a fixed namespace in `RUNNER_TEMP`, with an explicit protected owner-only DACL. It opens directory handles with `OPEN_EXISTING`, `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT` and no `FILE_SHARE_DELETE`. The core cannot infer share flags from a borrowed handle; the fixture's fixed opener and actual rename/delete tests establish this limited lifetime behavior. It never enables privileges, creates another account or opens provider configuration.

The 18 mandatory native cases cover bounded synthetic descriptor mutations; invalid handle; valid owner-only admission; distinct-directory mismatch; rename and delete refusal while held; rename and delete success after close; ACL change; sticky refusal after repair; Everyone, inherited, unprotected and null DACLs; inheritable handles; regular files; an actual directory junction; and thread impersonation. The generated descriptor cases exercise truncated offsets/SIDs/ACEs, foreign synthetic owner, callback ACEs, duplicate entries and oversize input without changing an OS account. The native process closes its exact handles and token handles, then removes only its tracked files/directories and the junction itself. A failed case or uncertain close fails the suite; cleanup does not recursively walk the namespace.

The supplementary Windows workflow retains its original pinned Bun, frozen install and portable framing/help tests and adds the required fixed MSVC build and native suite with an explicit inert TOML startup file. The compiler receives a cleared environment with only fixed system, include/library and fixture temporary paths; CI supplies deliberately invalid `CL` and `_CL_` values to verify their exclusion. Compiler and SDK-header identities are sampled before compilation and compared afterward. The build records the actual image, compiler, toolset and SDK versions plus compiler/header/source/executable hashes; `windows-2025` is not an immutable toolchain pin. Compiler output is drained with a 128 KiB total bound and a 60-second deadline; nonzero exit, output/cleanup uncertainty or changed source retains the build directory and produces no admitted build receipt. The fixed native child has bounded output, a finite deadline and actual exit plus stdout/stderr EOF/close joins. Ordinary platform runs execute only the result/parser property cases. The compiled build artifacts stay in the CI temporary directory and are not published.

These are sequential observations. They do not prove that security cannot change after observation, resistance to administrators or hostile same-user code, safe pathname traversal/creation, atomic publication, a durable journal, named-pipe authentication, Job Object containment, console custody, an installer or provider support. An admitted handle is not lasting authority after close. Product Windows installation and runtime guards remain unchanged.
