# macOS authentication qualification foundation

This scripts-only boundary implements a closed synthetic qualification sequence, private evidence journal and explicit metadata/status observer compositions. It has no command entrypoint, provider client, Keychain operation or production import. `observer.ts` requires an explicit status port; `native-observer.ts` supplies individually scoped and paired native process compositions only when called with fresh owner launch authority. Tests use explicit fixture ports or an opt-in synthetic native program. `LIVE_QUALIFICATION_CAPABILITY` remains unavailable. Completing fixtures always reports `liveQualificationProven: false` and `activationAuthorized: false`.

The six phases are preflight of two signed-out roots; owner-attested A login with B unchanged; distinct owner-attested B login and fresh detached A/B/A plus a concurrent pair; logout A and a joined interrupted A login; recovery of original A and logout B; final A logout, both signed out and exact owned cleanup. The 22 closed steps in `state.ts` specify the order. A joined interruption that actually authenticated is recorded separately and closes this sequence for deliberate recovery; it cannot pass as pre-authentication cancellation or trigger an automatic second login.

`identity.ts` accepts two genuine normalized `ClaudeAccountMetadataIdentity` tuples or null, plus one bounded private status result. It validates the closed tuple shape and canonical scalars directly, without raw metadata parsing, duplicated metadata normalization or synthetic JSON reserialization. It reuses the pinned status parser, enforces the 16-KiB/4-KiB status bounds, joined child and both output EOFs, and a declared 3–5 second observation deadline. It compares the two tuples, then matches normalized active reported email and organization to that unchanged identity. Both account and active email tags must differ between A and B. Missing fields, non-Claude.ai status and cache-A/status-B mismatch refuse.

`observer.ts` calls `readClaudeAccountMetadataIdentity({configDir, configHome: "isolated"})`, then exactly one required joined-status port, then a second genuine metadata read. It snapshots each tuple immediately and copies the bounded status bytes before the next await. The observer clears its owned proof-key and status-byte copies in `finally`; the projector also clears its own status copy. Caller-owned buffers remain unchanged. This is best-effort clearing of those buffers, not erasure of immutable strings or all runtime copies. It preserves the requested deadline, observes cancellation between operations and returns only run-local tags. Read or status failures produce closed errors without private diagnostic causes. The account reader bounds bytes and checks no-follow descriptor custody, but it currently ignores close errors; this composition cannot claim successful metadata descriptor closure or a hard wall-clock bound for filesystem IO. It does not race unfinished IO against a timer or manufacture cleanup proof.

The joined-status port receives the exact run/attempt/probe/profile/config scope, an abort signal and a declared 3–5 second deadline. It returns private stdout, stderr byte count, coherent exit, child/stream join facts and actual elapsed time. `observeNativePrivateClaudeIdentity` maps the separate native process boundary only after its actual admitted settlement, `cleanup: "joined"`, coherent exit, both clean EOFs, complete inspector collection and matching bounded byte/deadline evidence. It returns native detachment separately alongside the same-probe private identity projection. `observer.ts` itself supplies no default native status port. Neither composition grants owner, proof-key, persistence or launch authority; the caller must supply a fresh revalidation closure and final synchronous assertion. The owner's no-graphical-prompt observation remains separate.

`observeNativePrivateClaudeIdentityPair({first, second, overlapDeadlineMs})` joins two individual metadata/status/metadata observations to the actual retained-child overlap function. Pair preflight requires the same run, attempt, proof-key bytes and executable path/digest; profiles ordered A then B; distinct probe IDs; matching per-profile configuration bindings; and four pairwise nonoverlapping configuration/temporary roots. Extra native input fields, structural receipts and injected ports refuse before launch. Each input, key copy, environment and revalidation method is captured before the first await.

Both genuine metadata-before reads and asynchronous authority revalidations complete before the private launch rendezvous opens. Each process binding is prepared there. The coordinator then performs A's synchronous owner assertion and fixed start, B's synchronous assertion and fixed start, and immediately invokes `observeDarwinDetachedStatusOverlap` on those two actual instances. There is no await between those operations. No public callback hook or native witness override exists. A failed metadata read, authority check, partial launch, overlap or projection rejects the peer waiter, interrupts every retained child and still joins both observers and any started overlap operation. An ambiguous spawn or collection keeps cleanup uncertain; completed promises alone do not prove overlap.

Metadata and authority-revalidation ports must settle their own operations. Rejecting the pair rendezvous cannot cancel an arbitrarily unresolved port promise or establish a hard prelaunch wall-clock bound; the native target deadlines begin only after spawn.

Successful pair output contains both private identity/detachment observations and the actual admitted `observed` overlap receipt, with both witness identities exactly matched to the corresponding probe. It requires three joined additional inspectors, two joined targets and elapsed observation below the shared 100–1000 ms overlap budget. The original two-inspector per-child facts and 3–5 second target deadlines remain unchanged. This is the process layer's bounded A1/B/A2 observation under retained-child and second-resolution PID/start semantics, with the same limits on stronger PID-reuse or continuous-lifetime claims. It provides no evidence of distinct credential principals, graphical-prompt absence, simultaneous Keychain use or permission to activate managed macOS.

The explicitly named credential-free single and pair entries require every fixture port and always return `source: "credential_free_fixture"`. Their structural observations cannot produce `source: "native_process"`. The native entries use the real fixed process and overlap functions directly. Adapter-owned raw stream copies and yielded byte buffers are cleared on every settled outcome, including peer refusal; the original caller key remains owned by the caller. These are bounded buffer-clearing guarantees, not erasure of immutable strings or unrelated internal runtime copies.

Reported identity consistency is not an automated credential-principal lookup. The pin's status-field provenance is not established as a fresh credential-bound provider lookup. The separate owner attestations and eventual bidirectional logout/interruption observations remain necessary. No tags, account identifiers, email addresses, organizations, metadata or raw provider output appear in the public projection. A private checkpoint retains only exact private bindings, run-local keyed tags and closed observations. HMAC keys are separate local proof keys, never provider credentials.

Every step has a unique attempt, acknowledged checkpoint and binding revalidation before dispatch. A pending effect survives ambiguous persistence or observation. Checkpoint restoration authenticates and replays the bounded journal, requires a fresh owner epoch and exact binding revalidation, and admits only fresh reconciliation of the existing pending attempt. It never relaunches that attempt or signals a serialized PID. Invalid ordering and identity failures are sticky. A checkpoint is evidence and cannot establish native custody. `validateQualificationCheckpoint` authenticates stored evidence without adding a recovery transition; `restoreQualificationCheckpoint` additionally suspends incomplete work for a fresh owner.

The fixture driver obtains explicit binding observations from its injected revalidation callback. Saving the dispatch checkpoint introduces an await after those observations. A future real effect adapter must revalidate source, executable, environment and private custody again immediately at actual launch; serialized booleans cannot cross that gap as launch authority.

Native evidence uses a distinct version-2 binding and checkpoint envelope with the `native_qualification` mode and its own HMAC domain. `createNative`, `restoreNative` and the native checkpoint codecs reject fixture bindings and bytes; fixture version-1 serialization remains unchanged. Selecting native provenance proves no process, provider result or source contents. Native receipts continue to report `liveQualificationProven: false` and `activationAuthorized: false` until separate complete live acceptance and its evidence are reviewed. A completed account-isolation sequence does not qualify provider sessions or daemon recovery.

`prepareDispatchAuthority` requires the held native custody instance and a durably dispatched attempt. Each ticket captures the exact run, attempt, profile, probe, state generation and named receipt identity. Its one-use synchronous assertion checks the actual held owner and current receipt immediately before the fixed native start. Invalid use consumes the ticket; publication, cleanup mutation, release or uncertain custody invalidates prepared authority. Pair tickets may be prepared together and consumed independently without invalidating their sibling. Tickets prove only local custody; the closed driver must separately assert source contents and the exact runtime/environment binding.

A native restore with any pending attempt is recovery-only for that held instance. It cannot issue launch tickets or persist observations that clear or replace the pending attempt or advance its step. Releasing and reopening therefore cannot turn synthetic reconciliation into authorization for another login or logout. Resume from a durably settled boundary still requires the new held owner's epoch. This restriction does not reconstruct a lost child handle or prove whole-driver crash recovery; unresolved effects retain their recovery scope.

The guarded complete driver binds these native process/observer primitives: explicit absolute pinned executable with exact source, digest, inode and signature revalidation before every child; preserved real HOME and the existing environment allowlist; exact foreground login/logout and owner interaction; owner observation of no graphical prompts; same-owner interrupted-login reconciliation; and native logout followed by joined owned cleanup. It accepts only a fresh run; restored or uncertain attempts retain their existing recovery fence. It uses the native owner and local custody adapter described below. Receipt tags or fixture booleans never supply live authentication facts.

The separate first-preflight composition is narrower. `admission.ts` captures exact clean local source and current pinned executable bytes, then supplies a synchronous content, executable and environment fence for each fixed probe. Its signature provenance joins those exact bytes to the previously independently verified release artifact; it does not perform fresh signature, notarization or revocation checks. Captured source revalidation proves tracked content, modes and root continuity, not later Git HEAD, index, origin or remote-main state. Custody and one-use dispatch tickets remain separate authorities.

The native preflight result's `signatureRevalidated` field records that exact current-byte join to reviewed signed-artifact provenance. It does not record a fresh platform signature, notarization or revocation check. `realHomePreserved` records unchanged real HOME selection and the driver's restriction to its four owned roots and protected evidence scope. It does not claim a comparison of private home contents, a Keychain audit or absence of provider-managed writes.

The result fields `stdoutJoined` and `stderrJoined` record completion of the driver's owned stream obligations. Detached status and help probes must observe both actual captured-stream EOFs. Foreground login inherits the owner's descriptors and has no captured output reader; those fields require coherent direct-child collection and the exact inherited-terminal binding. They do not imply terminal EOF, descriptor closure or descendant containment. The owner remains held through the subsequent attempt-bound owner observation and durable settlement. A child timeout or pending native settlement cannot supply any of these join facts.

`preflight-run.ts` creates one fresh native run and observes the four private roots empty before persisting intent, persistence and dispatch checkpoints. It invokes only A then B version, login-help and logout-help probes. The collector requires exact version and logout grammar, actual child/stream joins and bounded output. Login-help projection retains at most 32 bounded flag declarations and argument kinds, without descriptions, placeholder names or raw output; extraction completeness never admits a capability. The runner stops with `admitted: false`, leaves step zero and its dispatched checkpoint unchanged, retains all roots and attempts owner release once. It reports primary failure and owner-release uncertainty separately. No login, logout, status, restore, settlement or removal operation is available through this runner. A retained dispatched checkpoint remains recovery-only under the native restore rule above.

The separate `first-login-run.ts` composes only fresh steps 0 and 1. Its strict collector retains the actual A/B runtime objects after six joined version/help probes; it cannot convert old diagnostic receipts into capability evidence. Two fresh native identity observations must report signed out before preflight settles. Inherited authentication stops the run without logout. One A login then uses the retained runtime and a fresh dispatch ticket. After coherent child collection, a fresh terminal challenge binds the owner's reported A sign-in to that run and attempt. The response is an explicit owner observation, not an automated credential-principal lookup or proof of a physical human. A tool-owned terminal alone does not establish that the owner can interact with it.

The first-login composition holds custody until the owner response and settlement finish. Interrupted, failed or uncertain work retains its exact recovery scope; bounded collection does not convert a still-pending settlement into a join. Success stops at step 2 with `qualificationComplete:false` and `activationAuthorized:false`. It exposes no restart or restore path, no second-account login and no cleanup operation. It remains a partial source API; the complete driver does not call it and reacquire its released owner. Actual first sign-in qualification uses the complete entry only after its source and operational admission.

`native-run.ts` exposes one complete fresh invocation with only repository root, source commit, executable path, environment and abort signal as input. It accepts no profile, step, runtime, result, operation or restore override. It holds the same private custody, captured source and genuine A/B runtime objects from six strict capability probes through the fixed 22-step journal. Each effect follows durable intent and dispatch; the actual native boundary consumes a fresh custody ticket and rechecks source, executable and environment after the final await.

The sequence performs A and distinct B login, fresh individual and concurrent identity observations, bidirectional logout checks, a deliberately interrupted A login, signed-out reconciliation, original-A recovery and final both-signed-out observation. Only step 9 admits actual retained-child overlap. Every detached observation from step 6 has an owner no-graphical-prompt window announced before targets start and answered after target, stream, metadata and inspector collection. A fresh challenge belongs only to its run, step and attempt.

The owner must explicitly arm step 13 before launch. Its terminal Ctrl-C is local only while that exact login child is active; other interruptions stop the sequence. The signal controller preserves handlers across child collection and handoff without forwarding a second TERM for an inherited terminal signal. If authentication wins the planned interruption, the driver persists the existing `joined_authenticated` result and stops. Crossover, uncertain effects and persistence failures retain the authenticated journal and exact recovery locator without replay, opportunistic logout or root deletion.

Normal completion reaches step 22 only after all four cleanup acknowledgements and the terminal checkpoint persist, then releases the owner once. `sequenceComplete` describes this account-isolation sequence. `ownedRootsRemoved`, interrupted-login reconciliation, process/filesystem cleanup and owner release remain separate facts. Cleanup becomes uncertain before per-root filesystem work and stays uncertain after partial removal or ambiguous persistence. Both native and fixture outcomes keep `activationAuthorized:false`; explicit fixture provenance cannot become native authority. Provider sessions, token refresh, daemon recovery and installed daily use remain separately unqualified.

Cleanup first requires the recorded native logout, fresh detached both-signed-out probes and every owned child/stream join. The existing cleanup attempt must be persisted before effects. The journal additionally requires `cleanup_root_intent` and `cleanup_root_removed` events for `profileA`, `profileB`, `temporaryA` and `temporaryB`, in that closed order and bound to the exact dispatched cleanup attempt. Final settlement requires all four removed states, `profileAndTemporaryRootsRemoved: true`, and `protectedEvidenceRetained: true`. The fixture orchestrator persists each intent before calling its explicit per-root observation port and persists each returned reconciliation afterward. Missing or failed ports retain the pending root; no fixture callback proves live durability. Partial or uncertain cleanup retains its exact recovery scope; it never widens deletion to `runRoot`, the proof key, unrelated paths or credentials.

`custody.ts` creates a fresh mode-0700 temporary run root, four fixed direct child roots and a random 32-byte mode-0600 noncredential proof key. It rejects temporary parents overlapping real HOME or current state before creation; restore requires the same fixed direct-child run namespace before acquiring an owner. It acquires the separate Mac receipt owner and uses `AtomicPrivateJsonReceipt` for bounded, authenticated checkpoint persistence. Key reads require a regular single-link current-owner file, exact length, no-follow descriptor/name continuity and successful closure. Source and executable fields are recorded bindings; this adapter does not independently prove executable bytes or signatures. It preserves real HOME, checks current private identities, snapshots checkpoint bytes before awaits and refuses checkpoint regression or binding replacement. Persistence must extend the current in-memory journal, including restore's suspension, and progressing incomplete work must use this held instance's owner epoch. An older valid checkpoint cannot clear recovery. Uncertain persistence poisons the current instance and retains its exact recovery path.

The fixed `removeRoot` operation requires an already persisted intent and revalidates the exact root before moving it to its fixed quarantine. It fsyncs the parent, checks the same quarantine inode, removes it and positively observes both names absent. The caller then persists `cleanup_root_removed`. Restoration accepts the exact original or exact quarantine, or both absent only after persisted intent; both present or a substituted inode refuses. No path is recreated. This filesystem operation does not prove that provider children exited: a future live caller must establish fresh child/stream joins separately. Tests use synthetic histories and fresh roots exclusively.

`runRoot` remains the private evidence scope containing the noncredential mode-0600 proof key, authenticated receipt and retained owner lock. Only after observed cleanup may the caller persist the final terminal checkpoint through the atomic file-and-directory-fsync adapter. While an evidence or recovery receipt remains, the owner uses `releasePreserving`; this does not relax `removeAndRelease` or authorize removal of retained evidence. Releasing custody clears its in-memory key copy and retains the protected disk key for later verification.

A completed restore treats the deleted profile/temporary roots as historical bindings. The custody adapter verifies current retained key/receipt/evidence custody and authenticates the terminal checkpoint; completed checkpoints cannot be updated or authorize root removal. It never recreates deleted roots, resets the baseline, relaunches a child or derives credential-effect authority from a terminal receipt. Retention in a temporary directory is not durable archival: missing key, receipt or evidence custody loses verification and fails closed. This unreleased synthetic contract provides no compatibility path for the former proof-key-deletion or blanket-root-removal claims.

The adapter design may reuse existing reviewed Darwin provider process paths where their contracts fit. This foundation neither requires nor admits the optional OOC1 helper experiment as live auth authority. Real foreground login and detached status transports must be assessed against these authentication-specific requirements before a runnable live command is introduced.

## Browserless account ceremony

Fresh 22-step runs use `createNativeManualBrowser` and authenticate the optional
version-2 binding field `browserMode: owner_manual`. The entry refuses an absent
mode before provider preflight, and every collected login must report the same
manual-browser binding. Existing native creators keep their previous policy.
Old version-2 checkpoint bytes and their HMAC domain remain unchanged; successful
deserialization does not upgrade a historical receipt or admit another login.

Each of the four login stages explains A, distinct B, interrupted A, or recovered A
before launch. The owner prepares a fresh private browser session and presses Enter.
Claude's printed URL must be copied unchanged into that session, rather than clicked
into the normal browser. The interruption stage requires Ctrl-C without opening
the link. The existing post-login identity challenges and interruption arming remain
in place. A new private window alone is insufficient if another private window
shares its cookies. Oompa changes no normal browser windows, cookies or preferences.

An owner-refused, dispatched login stays pending even when its exact process joined.
Keep its checkpoint, proof key, owner lock and profile roots. Do not replay, logout,
remove roots or adopt profiles to retry. A separately recorded retired disposition
may distinguish joined process custody from unqualified account selection without
rewriting that checkpoint. A later fresh run uses different roots and retains all
initial signed-out checks. No automatic recovery or cleanup path was added.
