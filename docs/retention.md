# Cloud retention

The hosted sync endpoint has been live as an open beta since 2026-09-03. These periods are cleanup targets for records that can expire without a user request. They are not hard deletion deadlines: bounded maintenance can take longer while it drains a backlog.

For the current marker-2 command rollout, the protected capacity gate consists
of both the two-zero-pass capacity evidence and its exact `.activated` receipt.
The first file alone is not effect authority: the operator must activate and
read back the exact-runtime singleton as described in `docs/hosted-sync.md`.

| Email send attempts | 24 hours | Delete after `expiresAt`. |
| Email verification attempts | 1 hour | Delete after `expiresAt`. |
| Email-code challenges | 10 minutes | Delete after `expiresAt`; successful verification consumes all live challenges for the address. |
| Device-bind challenges | 5 minutes | Delete after `expiresAt`; a completed challenge cannot be reused. |
| Idempotency receipts | 7 days | Delete after `expiresAt`, after the lost-response recovery window. |
| Pending remote commands | Through their deadline | Mark `expired` after the deadline when no provider effect was prepared. |
| Ordinary requester-retained applied, failed, ambiguous, cancelled, or expired remote commands | Until the exact requesting device acknowledges its hosted receipt proof, then at least 30 more days | Unacknowledged terminal evidence is not cleanup-eligible while its requester remains active. Current marker-2 acknowledgement is bound to the command ID, idempotency key, and request digest. After validating the stable enqueue response, the current browser derives that proof from its just-submitted request, or recovers the server-stored tuple from a requester-only hosted list after response loss or reload, without persisting a browser outbox or replaying the provider effect. Revoking the requesting device explicitly abandons a current receipt without falsely acknowledging it and starts the same 30-day retention clock. A pre-rollout terminal row whose requester had already been revoked stays non-growing and is deleted only after both the command's terminal update and the device's `revokedAt` are at least 30 days old. A typed operator-abandoned legacy effect uses the separately named clock and matching terminal security evidence below; it never claims requester acknowledgement. |
| Encrypted single-use Codex login handoffs | Readable only until the earlier of one requesting-browser read or the server-owned settlement time plus 5 minutes | Consumption clears the ciphertext transactionally. At the exact deadline the result is no longer releasable even if physical erasure is delayed; a transactionally registered scheduled mutation clears it and releases its logical-byte quota at or after that deadline. A legacy row without `resultExpiresAt` uses the deterministic terminal-update time plus 5 minutes without first growing the document; maintenance may register duplicate idempotent erasure calls only during that bounded compatibility window. The indexed bounded sweep remains a recovery path, so cleanup-target latency applies only to ciphertext erasure, never to readability. The non-secret terminal command evidence keeps its separate acknowledgement and retention contract. |
| Security events | 90 days | Delete by creation time. A converted terminal event that proves an operator-abandoned legacy effect is retained until the paired 30-day command cleanup can be applied atomically; an unrelated cross-table command with the same pre-rollout public id is not authority for that deletion. |
| Encrypted usage projections | 90 days | The daemon selects one compact projection per device and Codex account every 24 hours, and the server independently enforces the same sliding interval from receipt time. Each projection contains one daily row and at most eight current limits. Delete by server receipt time. Each accepted upload first releases up to 20 expired projections for the same account, so unrelated cleanup backlog cannot consume that account's quota headroom. |
| Encrypted devices, account projections, sessions, chunks, metadata, and key envelopes | Until authenticated account deletion | Retain to provide multi-device sync. Append-only compact-projection recovery preserves every older encrypted chunk, records the new epoch at the global head plus one, and leaves the acknowledged recovery gap visible. |
| Encrypted canonical-memory spaces and immutable operation history | Until authenticated account deletion | Retain the complete per-space Oh operation chain because v1 cannot prune a prefix without breaking exact replay and ancestry verification. | Encrypted per-device memory supervision summary | Until replacement, device-revocation cleanup, or authenticated account deletion | The daemon replaces its own bounded auxiliary summary under an independent revision. Stale summaries remain untrusted by the browser freshness fence, and a summary failure cannot suppress the ordinary device registry. |

Oompa credential creation binds a new user to its unique active unverified subject in the same user/account/deletion-capacity transaction. A predecessor user/account interruption without that binding blocks rollout readiness; after 24 hours, bounded maintenance deletes only the exact inactive orphan relationship and releases its subject, pair, user, and quota authority atomically, while fresh retries, verified identities, live challenges/sessions, devices, and ambiguous relationships are preserved. |

The post-observation receipt invariant applies to current marker-2 session and
device commands. During a server-first mixed-version rollout, marker-absent
device requests keep the historical enqueue-time acknowledgement expected by
already-loaded old browser code. Marker-absent session requests never had that
compatibility acknowledgement: an existing row stays non-collectible until its
same requesting browser device later loads the current app and observes it in
the requester-only recovery list. Refresh browser writers after the hosted
deployment and monitor unacknowledged command counts; a different device may
prove an old CLI outbox row exists but cannot acknowledge on its behalf.

Every newly admitted command physically reserves its maximum remaining
lifecycle growth in the command quota category and one future terminal audit
record in the security category. An unacknowledged terminal row consumes the
lifecycle reservation and carries an inline 256-character receipt-capacity
field until exact acknowledgement or explicit revocation abandonment. These
are real quota-accounted rows and bytes, not virtual counters. Pre-rollout
terminal rows for already-revoked requesters are the deliberate no-growth
exception described above; they never receive padding that the requester can
no longer consume.

An exact acknowledged pre-rollout no-effect terminal carries no newly added
cleanup field at a hard ceiling. Maintenance walks those rows with a durable,
bounded cursor, preserves the original acknowledgement timestamp byte for
byte, and deletes only the exact acknowledged compatibility shape after its
terminal update is 30 days old. An unacknowledged active-requester row remains
discoverable and retained beyond that age until its proof-bound
acknowledgement. Operator-abandoned effect rows retain a separately named
30-day clock and a matching terminal security event; they never masquerade as
requester acknowledgement.

Scheduled maintenance rotates its starting category and gives each eligible category up to 20 records within one hard 200-record transaction ceiling. Session commands, device commands, and their large lifecycle-capacity rows are independently capped at eight documents per transaction so a page remains below the provider read limit even at the maximum encrypted envelope. Account deletion, revocation, and direct quota audit use the same command-specific bound. Deletion and revocation also receive a reserved one-minute worker quantum. These bounds prevent starvation without promising a maximum wall-clock deletion time under sustained backlog.

## Local peer-action retention

Oompa keeps complete peer-action replay and causal detail for at least seven days after the action's latest state transition. Cleanup is opportunistic and transactional: a later new action admission in the same project may remove only older `applied`, `failed`, or `cancelled` actions whose whole removable subgraph is closed. Exact replays do not spend rate budget or trigger their own cleanup. Active actor turns, active target-turn origins, unsettled actions, unresolved queue or mutation evidence, and every recursively required parent and root remain pinned for as long as they are needed.

New peer actions are limited to 120 per project in a rolling hour, in addition to the per-actor and fan-out limits. That admits at most 20,160 actions across a full seven-day window. The 25,000-action hard project cap therefore reserves 4,840 rows, just over 40 hours at the maximum project rate, for pinned recovery and causal evidence. If protected rows consume the cap, admission fails closed; cleanup never discards them to make room.

When a terminal queue action becomes eligible, Oompa clears only its action foreign key. The queue row, its terminal or resolved effect evidence, and `message_actor='peer_session'` remain, so recent content-free attribution is still reconstructable after the detailed action record expires. After compaction, the exact action request, policy revisions, digests, causal graph, and same-key replay receipt are no longer available; the seven-day period is therefore a minimum replay window, not a permanent audit promise.

Session transcript and encrypted compact-projection retention are independent of the peer-action ledger. Every non-owner compact message keeps the v0.5-compatible `actor='autorespond'`; an optional bounded `actorKind` distinguishes `peer_session` and `provider_switch` for newer readers. Unknown bounded future kinds render as `other sender`, never as the owner, while malformed kinds reject the chunk. Pruning a closed peer-action subgraph therefore does not relabel its retained transcript message or make an older reader mistake it for owner input.

The daemon keeps frequent local observations for the live 1, 5, and 15 minute velocity views without uploading every poll. A successful observation is removed when it is older than 24 hours, falls beyond the newest 2,048 successful rows for its account, or would put retained successful payload JSON above 16 MiB. Failed poll markers use the same 24-hour window and a separate 2,048-row ceiling. Pruning runs at writable database open and after every usage observation. At the 256 KiB per-row input ceiling, the byte budget still holds at least 64 successful observations. The widest velocity calculation needs at most 23 observations at the fastest 50-second poll cadence, including its conservative 1.2-window boundary. A separate cadence ledger retains at most 128 upload anchors per local account. Anchor timestamps survive payload pruning and reduce transport, but they are not quota authority.

Each device-account binding holds one closed server admission object: the last accepted receipt time and the highest processed revision, digest, observed time, and `stored` or `coalesced` disposition. Exact stored replays, exact coalesced retries, conflicting same-revision payloads, and stale lower revisions are resolved before cadence admission. A higher revision inside the interval advances only this quota-accounted binding cursor and returns a typed `coalesced` receipt, which advances the daemon journal without creating a usage row. This makes a lost response safe to retry and prevents a later request from changing the payload or order of an already processed revision. Account metadata and generation patches preserve the admission object. Journal reconstruction reads its revision from the server and rejects regression.

Cloud capacity is checked against both record and logical-byte ceilings at the conservative exact-retention boundary. The maximally valid compact projection is exactly 8,120 plaintext bytes and encrypts to exactly 10,848 base64url ciphertext characters. A full logical snapshot document is conservatively bounded at 11,599 bytes. Server receipt times for one device-account source are at least 24 hours apart. Inclusive 90-day retention therefore holds at most `floor(90 days / 24 hours) + 1 = 91` projections per source, even when a modified client sends a burst or catches up many local anchors at one receipt time. Sixteen possible device sources produce at most 1,456 projections and 16,888,144 logical bytes for one Codex account before any row becomes cleanup-eligible. One account therefore occupies at most 8.05 percent of the 200 MiB open-beta per-user ceiling, and that ceiling holds twelve such accounts at once; a user running more accounts than that at the absolute worst-case envelope needs a raised tier. Across all 32 accounts, usage occupies at most 46,592 records, well inside the 3,200,000-record usage category. The per-write release batch covers all 16 sources if their oldest projections cross the boundary together.

`oompa auth delete --acknowledge-erasure` durably prepares an identity-scoped job and secret status capability before requesting deletion. Fresh identities pre-pay a dedicated identity/job reservation pair, and existing complete pairs remain unchanged. Legacy backfill instead adds a 2 KiB inline account-deletion reserve to the existing authentication subject and creates the dedicated job reservation. The inline reserve charges the subject's exact stored-byte growth to identity without adding an identity record; the job is charged normally. Every current non-revoked device retains its device/job/security/receipt quartet. These reserves are charged to their named quota categories until the exact delete or revoke transaction consumes them. Inline deletion removes the reserve while disabling the subject and advancing its epoch, proves that the stored subject does not grow, and exchanges the job reservation for the durable deletion job. Dedicated pairs and device quartets retain their category-matched exchanges with non-growing quota deltas. Account deletion also releases every unused device quartet before final quota-authority erasure. The first hosted deletion transaction disables the authentication subject and advances its epoch before scheduling bounded removal of every user-owned category. The job carries resizeable physical capacity at acceptance, keeps the same quota-accounted size through category changes, and releases that larger obligation before the smaller service-only completion receipt is inserted in the same transaction. Device revocation jobs use the same fixed-size lifecycle rule. Revocation does not grow session-head rows: every public head query derives `orphaned` from the revoked execution-device authority while the stored active/idle spelling remains byte- and record-neutral, and the revoked daemon cannot authenticate, lease, append, or accept commands. Pre-capacity jobs drain remaining categories without persisting a potentially growing intermediate spelling, so a predecessor job at a hard ceiling still converges. Exact retry after response loss reuses the same job; `oompa auth status` reports capability-only progress after authentication records are gone. Deterministic tests prove immediate authority revocation and incremental removal. Fresh-deployment and live completion remain mandatory revalidation gates for a deletion-lifecycle change before it can replace the live candidate. The [deletion backend acceptance](deletion-backend-acceptance.md) defines this gate as an exact-source deployment to a fresh official Convex backend, followed by actual public-handler deletion and unchanged scheduled cleanup of isolated synthetic identities. It proves native backend lifecycle behavior, including the inline legacy path; it does not claim SaaS authentication or production-identity deletion. The protected command-capacity receipt in `docs/hosted-sync.md` is an additional gate for the current command rollout.
